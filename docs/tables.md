# Tables
A table is one game played by several people in the same place, each on their own phone (October 2026): Party's games, and the card and dice games that seat friends at a table with the computer players. It is the duo match's cousin, without its pairing: a pair links once and keeps a room of its own, while a table is opened for an evening by whoever has the app and joined by anyone who scans its QR code, in a browser, with just a name.

A table is a room of its own, `crates/rooms/CODE/<game>` under a fresh four-letter code (`createRoom` in `rooms.js`), so it needs no new database rules: `{ v, app, created, host, rev, players: { uid: { name, pid, seat, joined, online } }, game, inputs: { uid: … }, say: { n, text, lang } }`. Seats belong to players, not devices, as at a pair's table: the same phone after a reload, or the same player on another device (their player id), sits back down in their own seat; a newcomer takes the lowest free seat, and a full table (a game's own limit: four for cards, more for a party) says so. One device runs the table, its computer players, its clocks and its narrator: the host's while it's online, else the lowest seat online; the next in line steps in only when nothing has moved for four seconds (the running phone asleep, or gone without a goodbye), and that phone keeps its screen on while it runs the table (the screen wake lock). Every change is a transaction numbered by `rev`, so a move worked out on a table that has moved on since is turned down rather than played twice; what everyone does at once (votes, clues) is written each to its own place, `inputs/<uid>`, with nothing to collide, for the running device to gather. A device running older code than the table is updated, as at a duo table. The table's code stays in the page's address (`?table=CODE`), so a reload sits down again. A party is a table too (`crates/rooms/CODE/party`, on Party's page), and the tables of the games it plays sit beside it in its room (`crates/rooms/CODE/bones`, or a duo match's branch): the party's branch says which is being played (`playing`), and a page in the party follows it (`party-link.js`, loaded only by a page with `?party=` in its address, through `menu.js`).

Sitting down at a table takes one round trip to the database for a player already in their seat (October 2026): the table is read first, and someone it already seats sits straight down, presence marking them here, with no transaction (`join` in `table.js`). That's every phone a party sends to a game its host started (the host deals that table with everyone in it: README, Party), and every reload; anyone else sits down by the joining transaction, on the table already read. The transaction alone took two round trips on a page that had read nothing yet: a transaction's first try on an empty cache is a blind guess the database turns down.

`table.js` is the table itself and has no page in it, so the tests can seat a whole party in Node (`tests/table.mjs`: seats, the running device and the next in line, two moves on the same table, inputs at once, leaving, a player's other device, newer code; on `tests/fake-db.js`, the database in memory with as many devices as a test needs, refusing and storing what the real one does: `memdb.js`, as an offline party's host keeps it). `table-ui.js` is what a page needs around it: the name a guest goes by (asked once, kept on the device), the invitation (the QR code, the code in large letters, Copy link and Share, who's at the table, the game's own Start), the wake lock and the narrator, whose lines (`say`, numbered) every page shows and the running phone speaks, queued so one line doesn't cut off the last. `qr.js` draws the QR code from `vendor/uqr.js` (uqr 0.1.3, MIT, after Project Nayuki's encoder), error correction M, black on white in every theme (a camera reads light-on-dark codes poorly), each row's dark runs joined into one path so it stays sharp at any size; the link it carries is the page's own with the table's code.

What's at a table can be read by anyone who has its code and a browser's developer tools, hidden cards and roles included, as with a pair's room: the database has no accounts to tell players apart. These are games among friends at one table; Company's roles and the cards in a hand are hidden by the page, not by the database.
