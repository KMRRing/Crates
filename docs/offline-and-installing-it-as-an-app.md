# Offline, and installing it as an app
Every game works offline once the app has been opened online once, from the home screen too: `sw.js` (a service worker) keeps every file of every page on the device, about 29 MB. That's the pages and everything they load, the font (served from `fonts/`, not Google), the knowledge base Origin, Almanac and Order read, every knowledge bank and all of Gambit's chess puzzles. Until October 2026 the list was every file of certain kinds outside `kb/`, so the four games that read `kb/` directly never opened offline. Now `tools/offline.mjs` finds what each page loads by reading it (its scripts and styles, every import, worker and fetch, any string naming one of the app's files), wherever it lives, and `tests/offline.mjs` fails if a page loads something that isn't there, or loads a file by a path built as the code runs that isn't accounted for. Offline, a page that isn't kept opens the games screen instead of the browser's error page, since an app on the home screen has no Back. What needs a connection: playing together, watching, syncing between devices, and Wikipedia's pictures not yet shown (each is kept once it has been, and Keep pictures offline in Settings keeps them all). Offline, solo play works fully and Play together says it can't reach the server.

An update downloads only what changed. `sw.js` lists every file with a hash of its bytes, and a file already on the device with those bytes is copied from the old version instead of fetched again (every update used to fetch the whole app, and it changes many times a day). A changed file is fetched at an address carrying its hash, so no cache on the way can hand back an older copy, and the old version is deleted only once the new one is whole: if a new version is ever left incomplete (an older one taking over while it filled can empty it), it's completed when it takes over, and offline the old copy stays and answers for what it lacks. A new copy fills in two stages, so a page waiting for it can say how many files changed before any downloads: every file is looked for on the device first, then only the rest is fetched, and the worker tells the pages as it goes (files looked for, found, to download, downloaded, the bytes so far, the file on its way) and, if an install fails, why (the file and what the site answered). A page can also ask the worker in use its version, its list of files and whether its copy is whole, and ask it to fetch what its copy is missing. The logic is in `tools/service-worker.js`; `tests/offline.mjs` runs it against a stand-in for the browser's storage and the network.

The site installs as an app called Codex, with every game and the games screen inside:
- Windows: open it in Edge or Chrome, then the install icon in the address bar (or menu → Apps → Install). It gets its own window and a Start menu icon.
- iPhone: open it in Safari, Share → Add to Home Screen. (A home-screen app keeps its own saves, separate from Safari's.)
- Android: Chrome offers Install app.

The games screen (tap a game's name) has an Update button. It first compares this device's version with the site's: the site's read from its `sw.js`, fetched past every cache, the device's from the service worker in use. When they're the same it says so in a line under the buttons (Codex is up to date: version 0256e95) and changes nothing; offline, or with the site not answering, it says that and changes nothing either. When the site has a newer version, the update goes through the service worker's own install, so only the files that changed are downloaded, and the rete says where it has got: the two versions and how many of the files changed, the files found already on the device, the changed ones downloading (with the megabytes as they come), installing, switching to the new version, and reloading, back onto the games screen. A version that has already downloaded in the background just switches, and one still downloading in the background is followed, not started again. When the version in use is the site's but its copy is missing files (it took over offline), Update fetches just those, in the line, and nothing reloads. Saves, stats, settings and Wikipedia's pictures are never touched.

Until October 2026 the button emptied every stored copy, fetched the whole app, then removed the service worker so the new one installed from scratch and fetched it all again: 29 MB twice for a one-line change. It could also sit on "Starting the new version" for minutes. That was the browser's queue: a service worker registration runs its jobs one at a time, and removing it waits behind an install still running, here the background download of the very version Update had come to fetch (the app opened, found the new version and started on it; Update, pressed a moment later, waited for that download to end, which on a slow connection takes minutes, and for ever if a file never comes). Now nothing waits on that queue (the registration is asked of the browser directly), and every wait has a limit: a download with nothing coming in for 30 seconds (after 8 it names the file it's waiting for), a browser that hasn't started the new version within 20 seconds, a worker that doesn't answer within 3, a switch not confirmed within 8 (it reloads anyway). One that runs out says so and falls back to the full refresh, worded stage by stage: it checks the site still answers, clears the stored copy (not the pictures), removes the service worker (waiting no more than 3 seconds for the browser), fetches this page's own files past the browser's cache and reloads, so the newest version installs from scratch. The full refresh never empties anything without the site answering first, and it isn't used when the site refuses a file of its own version (a push under way, an outage): it couldn't install that version either, and would leave the device with no offline copy, so the device stays on its version and the line says why.

Updates otherwise happen by themselves: a new version is fetched in the background and waits; it takes over when the app goes off screen and the page reloads onto it when it comes back (taking over mid-game could mix old and new code). When a partner's device is already on a newer version, the game switches straight away (`reloadFresh` in `pwa.js`), the way Update does, under the rete from the start. A page shows the worker's counts only while it waits for an update, since a new version also fills in the background as a page opens, often while it joins a table, whose words they would take over. Tried in Chromium on a local server with a local `sw.js`: two files changed and two downloaded; already up to date; the site's `sw.js` answering 500; offline; a copy missing files; a download slowed, stalled and refused; Update pressed during the background download and during a first install; and no service worker at all.

`sw.js` is written by the workflow `.github/workflows/pages.yml` and by nobody else: on every push to `main` it checks the banks against `kb/`, runs the tests of what the push changed and, only if they pass, rebuilds `sw.js` (the file list, each file's hash and a version from them all) and commits it as github-actions[bot]. Pages serves `main` as pushed, but installed copies only move to a new version when `sw.js` changes, so a push that fails a test never reaches them; and since nobody else writes `sw.js`, nobody collides on it. Which tests a push runs (Korbi, 24 October 2026: running all of them on every push was too slow; again on 29 October: still about nine minutes whenever a shared file changed, which 39% of pushes did, and uptime isn't important here; and as a standing rule, "unless I specifically say otherwise just run the tests that take less than 5 seconds by default"): `tools/pick-tests.mjs` reads the files changed since the bot's last `sw.js` commit (so a run a newer push cancelled is never skipped) and picks, from the tests that take under five seconds (`tools/test-times.json`, written by `node tools/pick-tests.mjs --measure`: 96 of 149), the quick tests that read every page (`syntax`, `imports`, `wide`, `days`); the tests of what changed, which for a game's own file are `tests/<game>*.mjs` and for a shared file, a bank, `tools/` or `kb/` are the tests that load it, found from the file names each test (and each file it names) mentions, quoted, so `law-bank.js` finds `fair-options` and `kb/links.js` finds `kb`; and one twentieth of the other tests, a different twentieth each push (the commit count picks it), so every test gets its turn within twenty pushes. The 53 tests of five seconds or more (Factor, Manifest, Refinery, Cartel, Punt, Topple's, Gambit, Guilloché, Timegrapher, Trumps (hard), River, Big Two, Contract and `offline`, which together are 60% of the suite's time, most of them whole-game simulations) run only on request (`--slow` adds the slow ones named for or loading a change, `--all` everything) and in the nightly run. Replayed over the 475 pushes since 10 October, a push ran 63 tests and about 900 seconds of test time; it now runs 11 and about 44 (95% less; the worst push, 112 seconds). Why that is safe enough: of 594 pushes to date 16 failed their tests, 14 of them one afternoon's bank rewrites as the fairness check was tightened, and a failing push never reaches installed copies; a break the picked tests miss is found by the nightly run, a day at most. The price: `offline` (installed copies open with no connection) is slow, so a change that breaks offline play now waits for the nightly run. `node tools/pick-tests.mjs --run <changed files>` runs a push's selection locally in a few seconds, and `tests/pick-tests.mjs` holds the picker to it (a change finds its own tests, no slow test runs by default, a shared file no longer runs everything, the slices come round to every quick test). `tests/syntax.mjs` parses every script in one process (`vm.SourceTextModule`) rather than starting Node for each one: 33 seconds became under one. The whole suite runs every night at 02:23 UTC and on demand (`.github/workflows/all-tests.yml`, "Every test" under Actions), publishing nothing, and prints each test's time; it is what finds a game change that broke a game it doesn't own, and its failure email is the signal. `node tools/build-sw.mjs --local` writes one to try offline play.

Several Claudes can work at once, one app each: `CLAUDE.md` holds the rules (shared files one at a time, pull and rebase before pushing, never force-push, never commit `sw.js`, rebuild built files rather than merge them, test before pushing).
