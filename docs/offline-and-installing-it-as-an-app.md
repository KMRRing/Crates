# Offline, and installing it as an app
Every game works offline once the app has been opened online once, from the home screen too: `sw.js` (a service worker) keeps every file of every page on the device: the pages and everything they load, the font (served from `fonts/`, not Google), the knowledge base and every bank, all of Gambit's chess puzzles. `tools/offline.mjs` finds what each page loads by reading it (its scripts and styles, every import, worker and fetch, any string naming one of the app's files), wherever it lives, `kb/` included; `tests/offline.mjs` fails if a page loads something that isn't there, or loads a file by a path built as the code runs (`RUNTIME` there, `offlineFiles` in `tools/offline.mjs`; CLAUDE.md, "Offline") that isn't accounted for. Offline, a page that isn't kept opens the games screen instead of the browser's error page, since an app on the home screen has no Back. What needs a connection: playing together, watching, syncing between devices, and Wikipedia's pictures not yet shown (each is kept once it has been, and Keep pictures offline in Settings keeps them all). Offline, solo play works fully and Play together says it can't reach the server.

The site installs as an app called Codex, with every game and the games screen inside:
- Windows: open it in Edge or Chrome, then the install icon in the address bar (or menu → Apps → Install). It gets its own window and a Start menu icon.
- iPhone: open it in Safari, Share → Add to Home Screen. (A home-screen app keeps its own saves, separate from Safari's.)
- Android: Chrome offers Install app.

**Updates** (the logic is in `tools/service-worker.js`, run against a stand-in for the browser's storage and the network by `tests/offline.mjs`):
- An update downloads only what changed. `sw.js` lists every file with a hash of its bytes, and a file already on the device with those bytes is copied from the old version instead of fetched again. A changed file is fetched at an address carrying its hash, so no cache on the way can hand back an older copy. The old version is deleted only once the new one is whole: if a new version is ever left incomplete (an older one taking over while it filled can empty it), it's completed when it takes over, and offline the old copy stays and answers for what it lacks.
- Updates otherwise happen by themselves: a new version is fetched in the background and waits; it takes over when the app goes off screen and the page reloads onto it when it comes back (taking over mid-game could mix old and new code). When a partner's device is already on a newer version, the game switches straight away (`reloadFresh` in `pwa.js`). A page shows the worker's counts only while it waits for an update, since a new version also fills in the background as a page opens, often while it joins a table, whose words they would take over.
- The games screen's Update button first compares this device's version with the site's (the site's read from its `sw.js`, fetched past every cache) and, when they're the same, says so and changes nothing; offline, or with the site not answering, it says that and changes nothing either. When the site has a newer version, the update goes through the service worker's own install, so only the files that changed are downloaded, and the rete says where it has got. A version that has already downloaded in the background just switches, and one still downloading is followed, not started again. Saves, stats, settings and Wikipedia's pictures are never touched.
- Trap: the button once emptied every stored copy, fetched the whole app, then removed the service worker so the new one installed from scratch (29 MB twice for a one-line change), and could sit on "Starting the new version" for minutes. A service worker registration runs its jobs one at a time, and removing it waits behind an install still running, here the background download of the very version Update had come to fetch. So nothing waits on that queue (the registration is asked of the browser directly), and every wait has a limit (a download with nothing coming in, a browser that hasn't started the new version, a worker that doesn't answer, a switch not confirmed). One that runs out falls back to the full refresh: it checks the site still answers, clears the stored copy (not the pictures), removes the service worker, fetches this page's own files past the browser's cache and reloads. The full refresh never empties anything without the site answering first, and isn't used when the site refuses a file of its own version (a push under way, an outage): it couldn't install that version either, and would leave the device with no offline copy, so the device stays on its version and the line says why.

**Publishing** `sw.js` is written by the workflow `.github/workflows/pages.yml` and by nobody else: on every push to `main` it checks the banks against `kb/`, runs the tests of what the push changed and, only if they pass, rebuilds `sw.js` (the file list, each file's hash and a version from them all) and commits it as github-actions[bot]. Pages serves `main` as pushed, but installed copies only move to a new version when `sw.js` changes, so a push that fails a test never reaches them; and since nobody else writes `sw.js`, nobody collides on it.

Which tests a push runs (Korbi, 24 October 2026: running all of them on every push was too slow; again on 29 October: still about nine minutes whenever a shared file changed, which 39% of pushes did, and uptime isn't important here; and as a standing rule, "unless I specifically say otherwise just run the tests that take less than 5 seconds by default"): `tools/pick-tests.mjs` (CLAUDE.md, "Several Claudes at once", has how) picks the tests that take under five seconds (`tools/test-times.json`), the tests of what changed, and one twentieth of the rest. The tests of five seconds or more run only on request (`--slow`, `--all`) and in the nightly run (`.github/workflows/all-tests.yml`, 02:23 UTC; also on demand), which publishes nothing and is what finds a game change that broke a game it doesn't own. Why that is safe enough: a failing push never reaches installed copies, and a break the picked tests miss is found by the nightly run, a day at most. The price: `offline` (installed copies open with no connection) is slow, so a change that breaks offline play waits for the nightly run.
